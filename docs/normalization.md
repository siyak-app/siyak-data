# Arabic search normalization

Siyak normalizes Arabic text for search in two places:

- the **pipeline** fills `verses_fts` in `core.db` with `normalize(verses.text_clean)`
  (`pipeline/normalize.py`);
- the **app** passes every search query through its Rust counterpart before it
  queries `verses_fts`.

Query and index therefore meet in the same form. `verses.text_clean` itself is
Tanzil's Simple Clean text, stored verbatim; the normalized form exists only
inside the search index and is never displayed.

**The contract is `tests/normalize_vectors.json`.** Both implementations must
produce `expected` for every `input`. Every vector names the rules it
exercises (`rules`); a test checks that this list is exactly the set of rules
that change the input, so the documentation cannot drift from the code.
Vectors taken from the Quran name their origin in `source`
(e.g. `tanzil uthmani 2:153 token 1`); their `expected` values were written
by hand, not generated by the normalizer.

## Rules

Rules are applied in this order: **N10 → N11, N1–N9 → N12**. Removals and
letter mappings never interact (no mapping produces a removed character and no
removal produces a mapped letter), so N11 and N1–N9 can be applied in a single
pass with one translation table.

| Id | Rule | Characters | Why |
|---|---|---|---|
| N10 | Decompose Arabic presentation forms with NFKC, **only** for characters in these ranges | U+FB50–FDFF, U+FE70–FEFF | Text copied from PDFs and old software uses positional forms (`ﺑﺴﻢ`) and ligatures (`ﷲ`, `ﻻ`) |
| N11 | Remove invisible format characters | U+200B–200F, U+202A–202E, U+2066–2069, U+061C, U+FEFF | Zero-width joiners, bidi marks and the BOM come along with pasted text and split words invisibly |
| N1 | Remove harakat and other combining marks | U+064B–065F | Fathatan…sukun, maddah (U+0653), combining hamza above/below (U+0654/0655), subscript alef. The query `الصبر` must find `الصَّبْرِ` |
| N2 | Remove superscript (dagger) alef | U+0670 | Uthmani vowel sign |
| N3 | Remove Quranic annotation marks | U+0610–061A, U+06D6–06ED, U+08D3–08FF | Honorific signs, small high letters, pause marks, end of ayah, rub el hizb, sajdah sign, small waw/yeh, extended Quranic marks |
| N4 | Remove tatweel | U+0640 | Decorative stretching; also carries superscript alefs in Tanzil Uthmani |
| N5 | Unify alef variants | أ U+0623, إ U+0625, آ U+0622, ٱ U+0671 → ا | Users rarely type hamza/madda/wasla on alef |
| N6 | Alef maqsura → yeh | ى U+0649 → ي U+064A | Final ى/ي are used interchangeably in typing (and Uthmani writes final yeh as ى) |
| N7 | Teh marbuta → heh | ة U+0629 → ه U+0647 | Common typing variant |
| N8 | Hamza carriers → bare letter | ؤ U+0624 → و, ئ U+0626 → ي | Hamza spelling varies; users often omit it |
| N9 | Persian/Urdu letters → Arabic | ک U+06A9 → ك; ی U+06CC, ے U+06D2 → ي; ہ U+06C1, ھ U+06BE, ۀ U+06C0 → ه | Persian and Ottoman keyboard layouts produce these letters |
| N12 | Collapse whitespace | every run of Unicode `White_Space` characters → one U+0020; trim both ends | Removing pause-mark tokens leaves double spaces; queries contain tabs, no-break spaces etc. |

`White_Space` is the Unicode property (U+0009–000D, U+0020, U+0085, U+00A0,
U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000), which is exactly
what Rust's `char::is_whitespace` tests. Python's `str.isspace` is **not** used
because it also accepts U+001C–001F.

Everything else passes through unchanged: Latin text, digits (including
Arabic-Indic digits), punctuation, the standalone hamza ء, and characters such
as the basmala ligature ﷽ (U+FDFD), which has no decomposition. Case folding of
Latin text is left to the FTS tokenizer.

## Implementation notes for the Rust side

- Work on code points (`char`), not bytes or grapheme clusters.
- N10 is the only rule that uses Unicode normalization data. Apply NFKC to each
  character in the two ranges individually (e.g. `unicode-normalization`'s
  `nfkc()` on a one-character string), never to the whole string.
- N10 output can contain characters handled by later rules (`ﷺ` → `صلى الله عليه وسلم`,
  which N6 then changes; `ﹰ` → space + fathatan, which N1 and N12 then clean up).
- No global NFC/NFKC: two implementations built on different Unicode versions
  would otherwise disagree on rare characters.

## Properties (tested)

- **Idempotent:** `normalize(normalize(x)) == normalize(x)` for every vector and
  for every verse of the Uthmani and Simple Clean texts.
- **Simple Clean is only changed by letter rules:** applied to Tanzil's Simple
  Clean text, only N5–N9 fire. With the pinned text (version 1.1) that is
  N5: 15,738, N6: 2,595, N7: 2,344, N8: 1,855 characters; N9 never fires.

## Trade-offs (accepted)

The letter rules (N5–N9) find more matches but can merge different words. These
were accepted deliberately (M1a review):

- **N6** merges على ("on", very frequent) with علي (al-ʿAliyy): a search for
  `العلي` also matches `العلى`-spelled words; a search for `علي` returns every على.
- **N7** merges ة with ه, e.g. رحمة / رحمه ("his mercy").
- **N8** merges forms like سئل / سيل.

## Limitation: Uthmani vs. Imlāʾī spelling

The normalizer removes marks; it does not convert Uthmani orthography into
standard (Imlāʾī) spelling. Text copied from the Uthmani script may therefore
not match the Simple Clean index:

| Uthmani | normalized | Simple Clean | normalized |
|---|---|---|---|
| ٱلْعَـٰلَمِينَ | العلمين | العالمين | العالمين |
| ٱلصَّلَوٰةَ | الصلوه | الصلاة | الصلاه |
| يَـٰٓأَيُّهَا | يايها | يا أيها | يا ايها |
| يَـُٔودُهُۥ | يوده | يئوده | ييوده |

Bridging this would mean a spelling-conversion table, which is out of scope for
v1. Users typing Arabic on a keyboard produce Imlāʾī spelling, which matches.

## Changing the rules

A rule change is a breaking change for the app's search. It needs:

1. a discussion issue explaining the recall/precision effect;
2. updated vectors (every new or changed rule covered, including whole words
   from the Quran);
3. a matching change in the app's Rust implementation in the same release;
4. a rebuild of `core.db` (its `verses_fts` content depends on the rules).
